# La Fabrique extraordinaire

## En une phrase

Le poste de pilotage d'un projet logiciel construit avec Claude : l'amont du dev (des fiches de features, rangées et validées avant d'entrer dans le cycle), sa documentation en ligne, ses stories, ce qui attend la production, et un circuit de demande **suivi, contrôlé et traçable**, du besoin écrit par un Product Engineer jusqu'à la version en production.

Premier projet piloté : L'épicerie extraordinaire (`serge-fantino/epicerie-extraordinaire`). La Fabrique extraordinaire (« La Fabrique » en abrégé) est générique : un autre projet s'y branche sans changer son code.

## Principes (non négociables)

1. **GitHub pour le dev, La Fabrique pour l'amont.** GitHub reste la seule source de tout ce qui est dev : les stories sont des issues, le code des branches et des PR, les déploiements des workflows ; La Fabrique les affiche, les relie et les déclenche, elle ne les recopie pas (pas de second Jira, pas de doc dupliquée). L'amont, ce qui n'est pas encore du dev et peut ne jamais le devenir (les fiches de features, leur rangement, leur validation), vit dans La Fabrique, rattaché au projet (épique F4, #74). Quand une fiche devient une story, la story vit sur GitHub et La Fabrique ne garde que le lien. Une fiche reste une fiche : ni assignation, ni estimation, ni sprint.
2. **Chaque projet se décrit lui-même** dans un fichier `.fabrique.json` à la racine de son dépôt, versionné avec son code (format : `docs/fabrique-json.md`). Rien de propre à un projet dans le code de La Fabrique.
3. **Les actions sensibles restent dans le projet.** Promouvoir, déployer, migrer, lancer Claude : ce sont des workflows GitHub du projet, avec ses propres secrets. La Fabrique les déclenche par l'API GitHub et n'a **jamais** de jeton de déploiement (Cloudflare, clés d'API d'un projet).
4. **Traçabilité de bout en bout.** Fiche → demande → issue → branche → commits → déploiement sur int → validation → version en production → migrations : chaque étape est reliée et datée. Ce que GitHub ne garde pas (qui a validé quoi, qui a donné le go) est dans le journal de La Fabrique, jamais effacé ; les fiches gardent toutes leurs versions.
5. **Personne d'autre que le super admin ne met en production.** Les rôles sont donnés dans La Fabrique, par identifiant GitHub et par projet (F4.9, #84 : aujourd'hui encore un rôle par compte pour tous les projets) ; le super admin l'est pour tous.

## Rôles

- **Super admin** : tout, dont le « go » (promotion en production) et la gestion des rôles et des projets. Le premier est déclaré dans la configuration du Worker (`SUPER_ADMINS`, identifiants GitHub), jamais dans le code.
- **Product Engineer** : écrit des demandes (formulaire guidé selon le modèle du projet), les précise avec Claude, les déclare « prêtes pour Claude », valide sur int.
- **Tech lead** : relit les demandes et les PR, peut lancer Claude, suit la CI.
- **Testeur** : voit int et les demandes à valider, coche les critères d'acceptation, signale un défaut (issue reliée).
- Sans rôle : signaler un défaut depuis l'app d'un projet dont le compte GitHub voit le dépôt (étiquette *to triage*, 20 par jour) ; rien d'autre (connexion à La Fabrique refusée poliment).

Chaque rôle a les droits de ceux d'avant (`src/rights.ts`) : signaler un défaut (tout compte qui voit le projet) < testeur (int, critères, validation) < Product Engineer (demandes, priorités) < tech lead (Claude, Setup) < super admin (go, rôles, projets, apps).

**Perspectives** (F4.1, #75) : le rôle dit ce qu'on peut faire, la perspective ce qu'on voit (tableau de bord, onglets d'un projet). Elles sont standard (les mêmes pour tous les projets) et portent le nom d'une activité, pas d'un rôle : Product et Administration d'abord, puis Testing, Engineering, Architecture, Operations ; « All » garde la vue complète. Les perspectives d'une personne sur un projet suivent son rôle sur ce projet, sur la même échelle que les droits ; elle passe de l'une à l'autre dans l'en-tête. Une perspective masque, elle n'interdit rien.

## Architecture

- **Un Worker Cloudflare** (TypeScript strict) sert les pages et l'API ; **sa propre base D1** (comptes, rôles, perspectives, projets, journal des décisions, et les fiches de l'amont : `cards`, leurs versions et leurs liens, peu structurées : le texte en Markdown annoté et du JSON, en colonnes seulement ce qui sert à filtrer et à ranger ; export par projet). Aucune donnée d'un projet piloté n'y est copiée (pas de données des clients de l'épicerie) ; pas de retours de ses utilisateurs pour l'instant (campagnes de tests ouvertes : plus tard, avec leurs règles).
- **Une GitHub App « La Fabrique extraordinaire »** : connexion des personnes (OAuth de l'App, jetons utilisateur courts) et accès aux dépôts où elle est installée (jetons d'installation). Installer l'App sur un dépôt, puis le déclarer dans La Fabrique : c'est le lien avec un projet.
- **La Fabrique, fournisseur OAuth** des apps des projets (#65, `@cloudflare/workers-oauth-provider`) : une app par projet, enregistrée par le super admin dans le *Setup* du projet (*Connected app* : adresses de retour tirées de `application` du `.fabrique.json`, secret affiché une fois avec les commandes à lancer dans le projet, secret renouvelable) ; chacun déconnecte ses apps dans Settings → *Connected apps*, consentement au nom de la personne, seule portée `defects:report`, `/oauth/authorize`, `/oauth/token`, `/oauth/revoke`, `GET /api/me` ; clients, autorisations et jetons dans D1 (`oauth_kv`, pas de KV à créer). Jamais un jeton GitHub remis à une app. Un compte sans rôle ne se connecte que pour cela (consentement, *Connected apps*). Contrat avec l'épicerie : commentaire « Contract with L'épicerie extraordinaire » de #65, à ne pas changer sans le dire aux deux côtés.
- **Kit de signalement** (`kit/`, `docs/report-kit.md`, servi en `/kit/…` et `/guide/report-kit`) : le bouton « Report a defect » d'une app de projet, générique ; le projet recopie `fabrique-report.js`, `.css` et `-early.js` chez lui (CSP `script-src 'self'` suffit), le navigateur ne parle qu'au relais du projet (`GET` état, `POST` signalement), qui ajoute environnement et version et transmet à La Fabrique avec le jeton de la personne. Version dans la première ligne de chaque fichier ; jamais exécuté par les pages de La Fabrique. « Ça concerne » : le formulaire propose les notes de version en détail, sur int puis livrées, chacune avec ses changements (un changement se choisit : cité dans l'issue, gardé au journal) et les stories qu'elle déclare (champ `stories` d'une entrée ; rien n'est deviné d'après les branches ou les dates : une entrée qui ne le dit pas n'en a aucune), par `GET /api/projects/{project}/targets` ; le signalement porte `story`, `release` et `change` (rang du changement ; contrat : avenants dans #65). Mise à jour : le projet déclare le dossier de sa copie (`application.kit`, noms sans version) ; *Setup* compare sa version à celle de La Fabrique (lue sur la branche d'intégration, en cache 10 minutes) et propose une PR qui remplace les fichiers (commits et titre marqués `version.coulisses`, ce que le relais doit suivre dans la description). Onglet *Defects* du projet : les issues `bug`, leur story, leur version, à trier ; chaque défaut a sa page (`/defects/{n}` : l'issue lue sur GitHub à chaque visite, texte, capture servie par La Fabrique, commentaires ; aperçu de la story liée ; historique du journal), où se fait le triage (testeur et au-delà) avec le même choix, dit sur GitHub (commentaires sur la story et le défaut), *to triage* retiré, journalisé (`defect_linked`) ; le dernier lien (signalement, puis triage) décide de la story, dans *Defects* comme dans *To test*, qui montre aussi les défauts pas encore reliés.
- **Claude dans La Fabrique** (#74) : la spec fonctionnelle d'une fiche, écrite et révisée avec Claude par l'API Anthropic (`src/llm.ts`, `src/specs.ts`, SDK `@anthropic-ai/sdk`), avec la clé **propre à La Fabrique** (`ANTHROPIC_API_KEY`, secret du Worker, jamais affichée ; ce n'est pas une clé d'un projet, le principe 3 tient) ; modèle et quotas en variables (`CLAUDE_MODEL`, `CLAUDE_DAILY_CALLS` par personne et par jour, `CLAUDE_MONTHLY_BUDGET_USD` pour toute La Fabrique) ; réservé aux rôles qui écrivent des demandes ; chaque appel dans `llm_calls` (qui, quand, fiche, modèle, jetons, coût en millionièmes de dollar), jamais son contenu ; coût par fiche (page de la fiche, tableau) et par projet et personne (Settings → Claude, avec « Check the key »). Ce qui part chez Anthropic : le texte et les étiquettes de la fiche, sa spec, les titres des autres fiches et des stories ouvertes, les stories de la fiche (titre, étape, critères) quand Claude les revoit, le `CLAUDE.md` du projet. Claude cadre d'abord le besoin : au plus cinq questions, chacune avec son champ de réponse sous la spec ; les réponses repartent avec leurs questions et sont gardées avec la spec (`dialogue`), Claude ne les repose pas ; il s'arrête quand il en sait assez (`enough`, avec sa raison), ou quand la personne clôt les questions (« Enough questions », `closed`) ; au troisième tour, seulement les questions bloquantes ; tout se fait dans la page. **Claude travaille en tâche de fond** (`docs/decisions/0001-claude-in-the-background.md`) : la demande et les réponses sont enregistrées tout de suite (`claude_jobs`, journal dans `claude_job_events`) et mises dans la file Cloudflare `la-fabrique-claude`, que le Worker consomme (`queue()`, `src/jobs.ts` : un travail à la fois par fiche, deux en même temps au plus, trois essais à 30 s quand Anthropic est occupé, « Try again » ensuite) ; un Durable Object par fiche (`CardLive`, `src/live.ts`) pousse l'avancement aux pages ouvertes par WebSocket (`/cards/{id}/live`) ; quitter la page ne perd rien ; le tableau marque « Claude working ». La file est créée par le workflow de déploiement (jeton : *Queues → Edit*). Spec dans `cards.data`, versionnée ; « Make one story » en fait une issue au nom de la personne ; « Split into stories with Claude » (travail `spec_split`) propose des stories livrables seules, chacune avec ses critères (`cards.data.split`), relues et modifiées dans un aperçu (`/cards/{id}/stories` : cocher, titres, rubriques, ce que GitHub recevra) avant d'être créées ; ce que GitHub refuse reste proposé. Une fiche qui a déjà des stories : « Review the stories with Claude » (même travail) les relit contre la spec (leur titre, leur étape, leurs critères) : celles qui tiennent, celles à changer (un commentaire sur leur issue, relu avant envoi, au nom de la personne) et les nouvelles stories qui manquent ; journalisé (`card_stories_reviewed`). Chaque story renvoie à la fiche par son adresse permanente (`/c/{id}?rev=N` : la version exacte de la spec, « story 2 sur 3 ») ; la fiche liste ses stories (`card_links` `story`) avec leur étape et combien sont en production. Le statut d'une fiche se change sur sa page, et suit son travail (`advanceStatus`, journalisé avec sa raison) : *Shaping* quand on demande à Claude, *To validate* quand Claude en sait assez ou qu'on clôt les questions, *Validated* quand la story est faite ; il n'avance que vers l'avant, jamais depuis *Dropped* ni sur une fiche archivée ; une seule exception : une fiche *Validated* dont la feature change (son texte, sa spec, une ancienne version reprise) repasse en *To validate* (`reopenStatus`), et redevient *Validated* une fois ses stories revues.
- **Webhooks GitHub** de l'App (push, issues, workflow_run, pull_request) pour l'état en direct ; lecture à la demande sinon.
- Front : HTML/CSS/JS sans build, comme l'épicerie ; pages rendues par le Worker, graphiques en SVG côté serveur ; style sobre (voir Design).
- Lectures GitHub mises en cache dans D1 : par commit quand le contenu ne change plus (`.fabrique.json`, documentation, lignes modifiées par jour), sinon en instantanés par projet (`snapshots` : stories, production, activité, livraison, versions) rafraîchis par les webhooks et une courte durée de vie.

Permissions de l'App (le minimum) : Metadata (lecture), Contents (lecture et écriture : proposer un changement de `.fabrique.json`), Issues (lecture et écriture), Pull requests (lecture et écriture : ouvrir la PR de ce changement), Actions (lecture et écriture : déclencher un workflow du projet), Checks (lecture). Pas d'administration, pas de secrets. La Fabrique n'écrit jamais directement sur une branche d'un projet : un changement de sa configuration (cycle de vie depuis Setup) est une PR ouverte au nom de la personne, sur `integration` ou la branche de production, que le projet relit et fusionne.

## Sécurité

- Liste blanche par identifiant GitHub ; un compte GitHub sans rôle n'entre pas.
- Lancer Claude coûte et écrit du code : réservé aux rôles qui le peuvent, plafond de demandes en cours par projet. Claude dans La Fabrique (spec d'une fiche) : rôles qui écrivent des demandes, quota par personne et par jour, budget mensuel, chaque appel compté.
- Aucun secret affiché ni journalisé ; les jetons GitHub restent côté Worker.
- En-têtes de sécurité et CSP stricte dès le départ : `script-src 'self'`, aucun script en ligne ni `eval` ; trois scripts servis : `/fabrique.js` (barre de chargement, pages enchaînées sans quitter la page en cours, menu de la branche de référence, formulaires `[data-busy]` envoyés une fois, travail de Claude en direct `[data-live]` par WebSocket), `/request-draft.js` (brouillon d'une demande ou d'une fiche gardé sur l'appareil) et `/board.js` (déplacer une fiche sur le tableau, au pointeur ou au clavier ; rangement gardé sur l'appareil).

## Conventions

- Langue de base : l'anglais (équipe internationale) pour le code, l'interface, les nouveaux documents techniques, les issues, les PR et les messages de commit ; ton direct. Les fondations (ce fichier, `docs/fabrique-json.md`, l'épique F0) restent en français. Ce que La Fabrique écrit dans un projet piloté suit la langue de ce projet (une demande reprend ses rubriques et sa signature).
- Ne jamais écrire d'identifiant, d'e-mail ou de secret dans le code : variables et secrets du Worker.
- Stories : épique (étiquette `epique`) et stories numérotées `F<lot>.<n>` (`F0.1`…), chacune avec ses critères d'acceptation, rattachées à leur épique comme sous-issues.
- La Fabrique se pilote elle-même (`.fabrique.json` à la racine). Notes de version au format Fabrique dans `docs/release-notes.json` (format : `docs/fabrique-json.md`) : toute PR qui change quelque chose de visible ajoute en tête une entrée `0.N+1`, en anglais, avec la date et l'heure (Paris) de sa fusion dans `main` (pas de branche d'intégration) et ses stories (`stories`, numéros d'issues, `[]` si aucune ; exigé depuis 0.45) ; `/api/version` répond ce numéro. Les tests (`test/self.test.ts`) vérifient le fichier.

## Design

Sobre et lisible, au service du suivi : un tableau, des états en pastilles, des liens vers GitHub. Les fiches de l'amont : un bristol blanc sur le fond beige, le texte et des étiquettes (type, statut, domaine, segment, version), sans effet réaliste ; déplacées librement, rangées par une dimension puis une autre pour croiser, filtrées. Repris de l'épicerie : fond `#F3F4EE`, encre `#18211B`, accent `#C23D17`, bon `#1E5A43`, moyen `#D9A93B`, alerte `#8A2A0F` ; Archivo pour le texte, IBM Plex Mono pour les chiffres et les identifiants ; formes arrondies, cibles ≥ 44 px, contraste AA.
